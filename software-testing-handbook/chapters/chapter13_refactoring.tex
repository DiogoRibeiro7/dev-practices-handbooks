\section{Opening: Motivation and Learning Objectives}
Refactoring for testability pays dividends: fewer brittle doubles, faster suites, and clearer ownership. This chapter explains how to spot seams, apply dependency injection incrementally, and measure the payoff with deterministic, CI-friendly helpers. By the end you will know how to refactor a handler without rewriting the whole stack and keep automation grounded in observable behaviour.

\section{Core Concepts}
\subsection{Finding and documenting seams}
A seam is any place where you can change behaviour without editing the caller. Look for resource creation (new clients, clocks, singletons) and loops that bake in concrete classes. Document the seam with a short note or issue so the team knows why it exists and what tests rely on it. Use interfaces or protocols to hide the dependency while keeping the calling code focused on business rules.

\subsection{Dependency injection patterns}
Inject dependencies through constructors, factories, or context managers. Prefer constructor injection for long-lived services, factory injection when you need per-call state, and context objects for thread-local setups. Always ensure the injection point is testable (no global state) and deterministic (seed clocks, fix randomness, re-use in-memory fixtures). Keep the production wiring separate from the test wiring so fast CI runs operate with fakes or spies while production still uses the real clients.

\subsection{Incremental refactors and verification}
Refactor in small steps: (1) extract the dependency interface, (2) accept it as a parameter, (3) add a temporary adapter so both old and new call sites compile, and (4) update tests to pass fakes. Verify each step with existing suites and add targeted tests for the seam you expose. Keep a changelog entry or commit note that records the refactor, why the seam matters, and which automation exercises it so future engineers can follow the intent.

\subsection{Refactor playbook for testability}
Use a repeatable method so refactors stay consistent across teams and releases.

\textbf{Find seams:} flag resource creation (clients, file handles), time and randomness, and direct I/O calls (network, filesystem, environment) as seam candidates.

\textbf{Refactor steps:} extract an interface/protocol, inject it via constructor or factory, add a temporary adapter to keep old call sites compiling, then migrate callers and remove the adapter once the seam is stable.

\textbf{Verify:} run the existing suite to confirm no regressions, then add seam-focused tests that exercise deterministic paths (fixed clocks, fixed randomness, fake I/O).

\textbf{Measure:} record the suite duration delta, CI stability delta (flake reruns before/after), and rerun pass rate so the refactor’s impact is visible.

\textbf{PR checklist:}
\begin{itemize}
  \item Seam candidates (resource creation, time, randomness, I/O) are identified and documented.
  \item Injection point exists, adapter added if needed, and callers migrated or tracked with a follow-up.
  \item Existing suite remains green; seam-focused tests cover deterministic paths.
  \item Measurement notes include duration delta, CI stability delta, and rerun pass rate.
\end{itemize}

\subsection{Measuring testability and automation telemetry}
Track the impact of refactors with simple metrics: how long suites run before/after the change, how many CI jobs now skip heavy dependencies, and the success rate of rerun harnesses built on the fakes. Add logging around the seam (e.g., which injectors execute) so you can correlate pipeline gates with code branches. Good instrumentation lets the team trust the refactor because you can see the deterministic inputs that keep automation stable. These metrics should map directly to Chapter 12 signals (critical path duration, flaky failure rate, cache hit rate).

\section{Worked Example}
The worked example in \texttt{examples/ch13/report\_handler\_before.py} shows a handler that constructs \texttt{DatabaseClient}, \texttt{EmailNotifier}, and \texttt{Clock} inside the method, which makes deterministic tests hard. The refactored version in \texttt{examples/ch13/report\_handler.py} accepts those collaborators via constructor injection, while \texttt{examples/ch13/fakes.py} supplies \texttt{FakeDB}, \texttt{FakeClock}, and \texttt{SpyNotifier} for CI. Run \texttt{examples/ch13/README.md} to see how the deterministic harness replaces real integrations in tests while the production wiring still uses \texttt{build\_default\_handler()}.

\begin{lstlisting}[language=python, caption={Refactoring checklist automation.}, label=lst:ch13-refactor-checklist]
from datetime import datetime, timezone

from examples.ch13.fakes import FakeClock, FakeDB, SpyNotifier
from examples.ch13.report_handler import ReportHandler, build_default_handler

test_handler = ReportHandler(
    db=FakeDB(records={"order-42": {"summary": "ok"}}),
    notifier=SpyNotifier(),
    clock=FakeClock(datetime(2026, 1, 1, 12, 0, tzinfo=timezone.utc)),
)
test_handler.run({"id": "order-42", "owner": "ops"})

prod_handler = build_default_handler()
prod_handler.run({"id": "order-42", "owner": "ops"})
\end{lstlisting}

The snippet shows the seam: tests create the handler with fakes, while production uses \texttt{build\_default\_handler()} for real wiring. The tests in \texttt{examples/ch13/test\_report\_handler.py} assert that missing records skip notifications, timestamps stay deterministic, and the notifier fires exactly once.

\section{Checklist}
\begin{itemize}
  \item Identify seams by tracking where the code instantiates external resources or writes to globals.
  \item Refactor incrementally so every change keeps the existing tests green and adds focused coverage.
  \item Document the seam (comment, changelog, ticket) and annotate which automations cover it.
  \item Inject deterministic clocks, randomness, and I/O helpers so rerun harnesses in CI can reproduce failures.
  \item Keep production wiring in one helper (e.g., \texttt{build\_default\_handler}) so tests can inject fakes without touching the live stack.
\end{itemize}

\section{Exercises}
\begin{enumerate}
  \item Take a handler that currently instantiates resources internally and refactor it to accept collaborators. Measure the test suite duration before and after.
  \item Add a fake `Clock` and verify the handler logs the timestamp deterministically during the refactor.
  \item Document a seam by outlining its purpose, the traits it hides, and the automation that exercises it.
  \item Create a small CI harness that runs the refactored handler with fakes and reports the dependency list in the artifact metadata.
  \item Explore how the handler behaves when you swap in a slow dependency; confirm that the injected fake keeps the automation fast.
  \item Pair with the owner of the impacted module to review the refactor before merging and capture their concerns.
  \item Write a squarely deterministic test that ensures the handler does not send notifications when the database query returns `None`.
  \item Explain why refactoring a handler for testability might require revisiting the readiness script from Chapter 6.
\end{enumerate}

\section{Summary}
- Refactoring for testability unlocks faster, more reliable automation and makes pipelines easier to tune.
- Incremental seam extraction plus deterministic injection keeps CI reruns stable and the code readable.
- Document the refactor so future engineers see the intention and know which automation covers it.

These refactors consolidate the CI signals surfaced in Chapter 12: fewer flaky failures, shorter critical paths, and more reliable smoke/regression selection.
