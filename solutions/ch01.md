# Chapter 01 Solutions

> ⚠️ **Spoiler alert:** This section solves the Chapter 01 exercises directly. Read at your own risk.

1. The risk profile should rank releases by sensitivity (e.g., payments, compliance, UX-critical) and list the suites (unit, contract, smoke) that cover each tier. Pair it with a risk-owner and the planned cadence.
2. Map availability → integration/observability suites, performance → regression/load, correctness → unit/property tests, documenting the SLIs beside each.
3. A narrative charter might say: “When we release the checkout flow, we will verify payment orchestration via smoke tests, monitor latency via the SLO dashboard, and capture any regressions with targeted integration suites.”
4. The existing feedback loops are (a) code review/test run, (b) CI pipeline, and (c) production monitoring; identify the slowest (often nightly regression) and trim it by splitting to smaller stages.
5. Sketch the pyramid with a thick unit base, mid-weight integration, thin e2e, and honeycomb slices for contracts, chaos experiments, and exploratory charters; annotate cadence per layer.
6. For a non-deterministic test, inject a fake clock, fix RNG seeds, and capture I/O inside temp dirs or mocks; document the before/after steps.
7. Refactor the long assertion block into helper functions named for the critical behavior (e.g., `assert_payment_status_ok`), which clarifies intent and speeds debugging.
8. Running `python examples/ch01/risk_score.py` prints a composite risk value; confirm the script reads the same inputs each run and gating logic (e.g., bail when risk > threshold).
9. `examples/ch01/deterministic_assertions.py` should execute without errors—run it with `pytest examples/ch01/` and ensure the assertions pass.
10. Identify two assertions such as `assert response.status == 200` and `assert payload['id'] == expected_id`; describe how they fail fast when the contract shifts.
